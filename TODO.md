- [ ] Curve editing follow-ups: the symmetric-edge handles (middle node, in handle only) are covered by markup and operation tests but not driven interactively because no editable generator produces a symmetric class yet (EDITABLE is only `square`); a straight edge can be bent without adding a node (select the ring at either end and pull its hollow handle) but that is not discoverable; nodes keep their numbers across undo only while the node count is unchanged.
- [ ] Make changing the tiling mode not flatten curves. Today a stored path that does not end where its class kind expects (ends at the far corner, or at the middle for a symmetric class) is re-read as a polyline through its anchors (`edgePath` in `editor/shape.js`), so a mode switch that changes a class's kind loses its curves. Investigate refactoring so the path data is stored in a normalized state that does not depend on the kind: every stored edge a path from [0,0] to [1,0] in the edge frame (t along the edge, n outward). One way: a symmetric class stores its half in HALF-EDGE units, i.e. scaled by 2 in both t and n (a similarity, so arcs would survive too), and the kind only decides how the path is read: a free class maps it onto the whole edge, a symmetric class onto the first half and completes it by the half turn. Then free <-> symmetric reads the same curve (scaled, not flattened). To settle: what a full curve should mean when it is read as a half and the reverse, the project-file version bump and the loading of version-3 files, the sanitizer's end-point rule (always (1,0)), the `at.kind` plumbing that `edit.js` needs today only to pick the end, and whether to keep one shape per mode instead (see the mode TODO).
- [ ] Crossing checks for curved outlines. `crossingProblems` / `selfIntersects` only see anchors, so once edges can be curves the check must skip any outline that contains a non-`L` segment (the user keeps curves from crossing for now). Later: `flattenPath` with a tolerance, then `selfIntersects`.
- [ ] Corner dragging (reshape the base tile by moving edge endpoints / tile corners). Edge curves already live in each edge's own normalized frame, so they follow their chord. Open: moving a corner changes the tile transforms of a glued tiling, so it needs vertex classes next to the edge classes and lattice parameters in the generators (the corner positions probably belong in `params`, not in the shape). Keep editor frames derived from the real prototile edges, never from a unit-square assumption (`MARGIN * side` in `tile-editor-svg.js` uses `edges[0]` only).
- [x] Mirrored glues in `classes.js` (a flipped tile meets a proper one in the same world direction; parity counts only reversing glues). Still open for the hat and other reflection tilings: mirror-symmetric constraints (see above) and the exact-placement question under Generators.
- [ ] Non-edge-to-edge tilings (row shift, Archimedean, Penrose): classes lock unmatched edges. Brick bond still lets the vertical edges be edited (the `canEdit` gate says otherwise).
